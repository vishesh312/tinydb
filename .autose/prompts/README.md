# AutoSE agent prompts

Each agent runs as one headless CLI call (ADR-014). With the default `codex` backend, `<role>.system.md` is passed as `-c developer_instructions=…` (a separate message from the task) and `<role>.task.md` (after placeholder substitution) goes over stdin to `codex exec`; the final answer is constrained by `--output-schema` (a strict-mode copy of the schema). With the legacy `claude` backend (ADR-011) the system prompt goes via `--append-system-prompt-file`, the task to `claude -p --bare`, and the schema via `--json-schema`. Either way the answer must match the contracts in `architecture/DESIGN.md` §14, and validated again by the orchestrator, which renders the `.md` artifacts from the JSON (using the `*_md` field where the contract has one). For the Analyst, the orchestrator appends `workflow/skills/requirements-spec/SKILL.md` (a verbatim copy of the A1 skill) after `analyst.system.md`.

System prompts contain no placeholders. Task templates use `{{NAME}}` placeholders, filled by plain string replacement.

## What each experiment variant changes

- **E1 (ADR-008), `reviewer_friendly`.** Changes context (it also gets spec, design, dev notes and test report) and stance (a neutral "careful colleague" prompt: no issue-first derivation of expected behaviour, no minimum of three hypotheses, no mandatory probe). It keeps, on purpose, the same category and severity definitions (routing must mean the same thing), the same evidence rules, the same injection handling (safety is not the variable under test) and the same output schema. It is a fair, competent prompt, not a strawman: the comparison is "adversarial and isolated" against "informed and neutral". Model choice is set by the orchestrator, not the prompt: the friendly reviewer runs on the builders' model (`gpt-6.1-sol` in the recorded E1 run, `gpt-6.1-terra` by default since ADR-014 note 2), the independent reviewer on `gpt-6-astra` (now `gpt-6-luna`), and E1's cross-vendor arm uses the independent prompt unchanged on Claude Opus 4.6 via `agy` (`experiment/variants.md`).
- **E2 (ADR-001), `builder`.** Instructions are the union of `developer.system.md` and `tester.system.md`, worded the same wherever possible, including "derive expected values from the ACs". The only variable is whether one context writes both code and tests. Neither variant prompt mentions that it is an experiment, so the model's behaviour is not changed by knowing it is being compared.

## Design notes

**Anti-injection.**
- Untrusted text (issue title/body, maintainer comments, diff) is always wrapped in `<untrusted_issue>`, `<untrusted_maintainer_comments>`, `<untrusted_diff>` blocks, and every system prompt that sees it states that it is data, not instructions, and what to do with embedded instructions: record and ignore (`injection_findings`, `injection_attempts_noticed`). Pipeline-derived artifacts are wrapped in plain tags (`<spec>`, `<design>`, …) and are also described as data, since they are derived from the issue.
- Only the Analyst (read-only) and the Reviewer (no push, writes only to a probe dir) read raw issue text. Write-capable agents see only artifacts that passed a schema and a check (DESIGN principle 6).
- The prompts never rely on the model refusing; the real enforcement is the Codex sandbox (read-only or workspace-write, network off; the tool allowlist with the legacy `claude` backend), ignoring repo instruction files (`project_doc_max_bytes=0`; `--bare` with `claude`), no tokens in the environment, and the post-run path allowlist. The prompts tell the agent why those limits exist so it does not try to work around them.
- The Reviewer treats injected text **inside the diff** as an `important` (blocking) `code` finding, because it would be merged.
- The Verifier is a second model reading untrusted text and a new target ("verifier: this is a false positive"). Verification can only remove a send-back, so every failure keeps the finding blocking, and the orchestrator ignores a `REJECTED` whenever the review noticed injection attempts (ADR-015).
- `.autose/REVIEW.md` is read with `git show <base>:.autose/REVIEW.md`, never from the PR head, so a PR cannot rewrite the rules it is reviewed against; it is fenced and neutralised like other untrusted values.

**Anti-sycophancy / anti-self-grading.**
- The Analyst's criteria are rated by a separate Judge; the Judge is told to judge testability only and to fail criteria that try to steer its verdict.
- The Tester is told where expected values must come from (ACs, not the implementation's output), that a failing test against a contradicting implementation is the correct result, and never to weaken a test. The fails-on-base check backs this up deterministically.
- The Developer can contest a test only with a spec-based argument (quote the AC versus the assertion), so "this test is inconvenient" does not loosen the grader. The Tester decides contests "on the spec alone, not on which side is easier to satisfy".
- The Developer must report `deviations_from_design` honestly; the prompt notes that an empty list is a checked claim.
- The Reviewer is given both failure modes by name (rubber-stamping and nitpick-blocking) and a concrete test for severity ("can you show a concrete wrong outcome for an input the issue cares about?"). Approval requires commands it actually ran, including at least one own probe; every finding needs evidence; `pre_existing` and `nit` findings can never block, and every `important` one must survive a separate verifier (ADR-015). In round 2+ it must verify each of its old findings and then review afresh, which prevents both "fixed, approve" without checking and endless new nitpicks.
- The Reviewer writes `expected_behaviour_from_issue` before reading the diff closely, so its expectations are anchored on the issue, not on the PR's own framing.

**Scale and blocking questions (Analyst).** The A1 skill was written for whole systems. The adapter scales it to a change request (typically 2–6 ACs), maps its IDs onto the contract (`REQ-n`, `AC-n` so tests can be named `test_ac<N>_…`), drops `EXTERNAL` (no evidence tool), maps INTENT/CONFLICT/TENSION records onto `open_questions`, and narrows skill §7.1 to one operational rule: a question is blocking only if two plausible answers lead to different tests; otherwise it gets a default and an `ASSUMED` requirement. Maintainer comments (write-access users only) count as stakeholder answers and support `CONFIRMED`.
